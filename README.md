# apted

Tailor a resume to a job description and refine it iteratively via chat.

## Architecture

Three components work together:

### 1. Next.js web app (`/`)

The main application. Built with Next.js 15 (App Router) + TypeScript + React 19 + Tailwind CSS 3.

**Pages:**
- `/` — Dashboard with recent resumes and search
- `/resumes` — Library of saved tailored resumes with PDF previews
- `/resumes/[version]` — Individual resume viewer with PDF, job description, AI insights, and application funnel
- `/applications` — Application tracking with Sankey funnel diagram and inline status updates
- `/master` — Master resume editor (prose-first: dump raw memories, generate bullets via LLM)
- `/builder` — Tailor a resume from a JD, refine via chat
- `/settings` — Render template selection, API key management (coming soon)

**Shared components (`src/components/`):**
- `AppShell.tsx` — Collapsible sidebar navigation (claude.ai style), wraps all pages
- `SiteHeader.tsx` — Shared top bar with active page indicator
- `PdfPreviewPane.tsx` — Reusable PDF viewer with export menu, zoom, resizer
- `ResumePreview.tsx` — Card-level PDF preview
- `FunnelChart.tsx` — Sankey diagram for application flow visualization

**Design system:** Material 3-inspired light theme. Black primary buttons, Inter/Outfit typography, 12px card radius. See `docs/design.md` for the full token reference.

### 2. Chrome extension (`/extension/`)

A floating content-script drawer that overlays job sites (LinkedIn, Greenhouse, Lever, Workday, Ashby). It scrapes JDs, tailors resumes, displays PDF previews, shows similar past resumes, and injects PDFs into application form fields.

- **Not React** — vanilla TS content script in a shadow DOM
- `drawer.ts` — All drawer UI (HTML, CSS, JS in one file, ~2300+ lines)
- `background.ts` — Service worker routing messages to web app APIs
- `scrapers.ts` — JD text extraction per site (company/title extraction is LLM-only)
- `pdf.ts` — PDF caching and object URL management
- Built with esbuild, loaded as unpacked extension in Chrome

### 3. Compile service (`/compile-service/`)

Minimal Node.js HTTP server running Tectonic (LaTeX → PDF) as a subprocess.

- `POST /compile` — raw `.tex` in, PDF out
- `GET /health` — health check
- Runs on port 8080 in dev, containerized in production

## How it works

1. Your **master resume** lives as one JSON record in Postgres. It is the only source of truth. The master editor is prose-first: dump raw memories into a textarea, hit "Generate Bullets," and the LLM converts prose into structured resume bullets (merged with existing ones).
2. `POST /api/tailor` takes a JD and runs a **two-phase pipeline**:
   - **Phase 1** (DeepSeek v4 flash): Reads JD + master resume skeleton, decides which sections/items are relevant
   - **Phase 2** (Claude Sonnet): Takes the filtered master + JD + relevant prior versions, produces a tailored Resume JSON with XYZ-formatted bullets and JD keyword weaving
3. The builder UI shows a chat panel and a live PDF preview. Each chat turn calls `POST /api/edit` with the draft id + instruction. The draft IS the accumulated state — chat history is not replayed.
4. Every edit pushes the prior JSON onto an undo stack (capped at 20).
5. "Save as version" snapshots the JD + current draft into `resume_versions` with an outcome (draft, applied, interview, offer, rejected).
6. The PDF is generated by serializing the JSON to `.tex` using Jake Gutierrez's resume template macros, then compiled with Tectonic in the compile service.
7. **PII redaction**: Contact info and org names are redacted before DB storage and LLM prompts, injected back only for rendering.

## LLM provider routing

- **Primary provider**: OpenCode Zen (`https://opencode.ai/zen/v1`) — OpenAI-compatible proxy
- **Tailor/Edit/Bullets** (quality-sensitive): `claude-sonnet-4-5` via OpenCode Zen
- **Structure selection** (which sections/items to keep): `deepseek-v4-flash` via OpenCode Zen
- **Fallback**: Anthropic direct for tailor, DeepSeek direct for structure
- Model IDs are NOT prefixed (e.g. `claude-sonnet-4-5`, not `opencode/claude-sonnet-4-5`)

| `TAILOR_RELEVANT_VERSIONS` | no | How many prior versions to send as framing hints (default 5). |
| `TAILOR_RANKER` | no | `overlap` (default) or `embeddings` (requires OpenAI key). |

## Run

```bash
# 1. Install
npm install
cd extension && npm install && cd ..

# 2. Copy env
cp .env.example .env.local
# Fill in DATABASE_URL, OPENCODE_API_KEY, COMPILE_SERVICE_URL

# 3. Apply migrations
npm run db:migrate

# 4. Seed an empty master resume
npm run db:seed

# 5. Start the compile service (separate terminal)
cd compile-service && node server.js

# 6. Start the web app
cd ..
npm run dev
```

Then visit:
- `/` — Dashboard
- `/resumes` — Library of saved resumes
- `/master` — Edit your master resume
- `/builder` — Tailor a resume from a JD
- `/applications` — Track application outcomes
- `/settings` — Template and API key settings

### Chrome extension

```bash
cd extension && npm run build
```

Load in Chrome: `chrome://extensions` → Developer mode → Load unpacked → select `extension/dist/`.

## System prompt constraints

Encoded in `src/lib/resume-rules.md` (the single source of truth, injected into all tailor/edit system prompts):

- The master resume is the only ground truth. No invented facts.
- Past versions inform framing/emphasis only.
- Bullets follow the **XYZ formula**: "Accomplished [X] as measured by [Y], by doing [Z]."
- JD keywords (nouns and verbs) are woven naturally into bullets.
- The `notes` field on experience/project items stores raw prose for the tailor to draw from. Never rendered on the resume.
- Must fit one page. No em-dashes. No inline bold in bullets. Prefer shipped real-user work over coursework.

## Contributing

### How work is created

All work is tracked in **Linear** (team: Premiumfriedrice, key `PRE`). Every feature, bug, or improvement gets a Linear issue before any code is written. See `docs/WORKFLOW.md` for the full workflow.

1. Search Linear to confirm the issue doesn't already exist
2. Create the issue with a clear title and description
3. Set priority: 1=urgent, 2=high, 3=medium, 4=low

### How work is worked on

Start from a clean `main`, create a feature branch, and optionally use a git worktree for parallel work:

```bash
git checkout main
git pull origin main
git worktree add ../apted-<name> -b feature/<name>
cd ../apted-<name>
npm install
```

Write a handoff doc at `docs/handoff/YYYY-MM-DD-<name>.md` so another agent can pick up the work in a fresh session. Include: branch, worktree path, Linear issue number, what exists now, what to build, key files, and how to test.

Commit messages use these prefixes:
- `feat:` — new feature
- `fix:` — bug fix
- `style:` — visual/UI-only change
- `docs:` — documentation only
- `chore:` — tooling, dependencies, config
- `perf:` — performance improvement
- `refactor:` — code restructuring without behavior change

### How work is completed

Before merging, verify:
1. **Tests pass** — `npx vitest run` (web) and `cd extension && npx vitest run` (extension)
2. **Type checking passes** — `npx tsc --noEmit`
3. **Build succeeds** — `npm run build` and `cd extension && npm run build`

Squash merge to main:

```bash
git checkout main
git pull origin main
git merge --squash feature/<name>
git commit -m "feat: <description> (<ISSUE-ID>)

<Full summary of what changed.>
"
git push origin main
git worktree remove ../apted-<name>
git branch -D feature/<name>
```

Comment on the Linear issue with a summary of what was merged.

### Key principles

- **Linear first**: No code without an issue
- **Test before merge**: All tests must pass, no exceptions
- **Handoff docs**: Every worktree has a handoff doc for session continuity
- **Squash merges**: Collapse feature branch commits into one clean commit on main
- **Don't break main**: Feature branches hold the risk; main should always be green
